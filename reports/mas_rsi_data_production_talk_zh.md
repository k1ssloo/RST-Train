## 页 1 · 封面

> Recursive Self-Improving Data Production
> 对抗递归进化：由求解、验证、改环境三个 agent 组成的多智能体系统

**一句话**：这不是一个数据集，是一个让任务在对抗中持续变难的生产系统。

**口播**

> 这套系统要解决的问题是：终端 agent 的高质量训练数据怎么规模化地造出来。
> 现在的做法是让模型生成任务、自己写标准解、自己写验收脚本，跑通就收进数据集。
> 我们加的是一个对抗环节：让求解者去攻击这道题，让改环境的 agent 去堵漏，
> 只有在给定预算内攻不进去的任务才成为训练数据。
> 四个关键词在下面：对抗递归进化、三个 agent、参数化实例、verifier 是唯一的 reward。

**四个 chip 分别对应**：ADVERSARIAL RECURSIVE EVOLUTION 是方法，THREE-AGENT MAS 是系统结构，
PARAMETRIC TASK INSTANCES 是让「写死答案」失效的技术手段，VERIFIER IS THE ONLY REWARD 是安全边界。

**口误红线**：不要说「我们提出了一个新的 RL 算法」。这是数据生产方法，不是训练算法。

## 页 2 · Motivation：能力的瓶颈，已经从模型转移到题目

**一句话**：真正要提高的不是题目的长度或数量，而是「合格」这个标准本身的强度。

**口播**

> 先把话说大一点：现在限制 agent 能力的，已经不是模型，是题目。
>
> **能力从哪里来。** 终端 agent 要学的不是知识，是行为——在信息不全的环境里试探、判断、
> 纠错、收尾。这类行为只出现在「真的把一件事做完」的过程里，也只能从这样的过程中学到。
> 而模型越强，还能提供梯度的题越少。所以能力的边界，越来越取决于我们造得出多难的题。
>
> **难在自洽，不在数量。** 一道题不是一段文字，是一个自洽的小世界：目标说得清、环境立得住、
> 确实有一条走得通的路、而且有人能客观判定走通了没有。人来写，一道题的成本高到无法规模化；
> 交给模型批量生成，这四件事很容易各说各话。而最常见的失效方式不是「太难」，是「看起来合格」。
>
> **第三块才是我们要攻的地方。** 今天判定一道题合格的方式是：存在一个正确解，验收脚本认它。
> 这只证明了**有路可走**，没证明**必须走这条路**。如果照抄答案、伪造产物也能通过，
> 那么这道题给出的分数就不再代表能力；用它训练，模型会朝「让验收通过」进化，
> 而不是朝「把事做成」进化。
>
> 所以要提高的不是题目的长度或数量，是「合格」这个标准本身的强度：
> 不仅要存在正确解，还要在给定预算内找不到廉价解。
> 难度也跟着换了定义——不看标准解有多长，看**最短的通过解**有多长。

**三块的作用**：前两块（能力从哪里来、难在自洽）任何人都会同意，是共识；第三块
（「合格」本身有漏洞）才是这份报告的主张。讲的时候前两块可以快，第三块要停一下。

**可能被问到**

- *「RST 论文不是已经有反捷径检查了吗？」* 有，而且是契约强制的。但它们只对标准解验证过，
  从未被负例测试过。是没有失败用例的单元测试。（这是全场最重要的一句回答）
- *「难度换成最短通过解，怎么测？」* 需要一个攻击者，这就是第 3 页的第一个 agent 的第二种模式。
- *「加长任务不就是加难吗？」* 第 7 页有数据：标准解从 50 行长到 400 行，成功轨迹的中位轮数只从 9 涨到 14。

**口误红线**：不要把「模型学到的是 verifier 的形状」说成已测量的结论，这是机制推断。
已测量的是失败画像（第 7 页）。

## 页 3 · The System：三个 agent，一个 verifier

**一句话**：Solving 只产生行为，Verify 只裁决，Environment 只改环境；LLM 的意见永远不进 reward。

**口播**

> 系统里有三个角色，加一个不是 agent 的 verifier。
>
> Solving Agent 在沙盒里做任务。它有两种模式。正常模式尽力解题，成功轨迹既是训练数据，
> 也成为后面说的「证人」。攻击模式只给 1 到 8 条命令的预算，只能看指令和环境，
> 用最短最懒的方式试图骗过 verifier。攻击模式每成功一次，就产出一个反例。
>
> Verify Agent 是唯一的裁决者。它做三件事：在多个环境实例上跑标准解，给出可解性证书；
> 回放攻击轨迹，判定它是反例还是合法的快解；检查修复后的 verifier 是否还让所有证人通过。
> 它只输出逐项 check 结果，不输出意见。
>
> Environment Agent 是唯一能改任务的角色。提出更难的任务；收到反例后写一条新 check，
> 让反例失败而标准解和证人通过；把写死的 fixture 改成按 seed 生成的参数化实例，让常数不再是常数。
>
> 分工的原则写在下面：LLM 的意见永远不进入 reward、loss mask 或评测分。reward 只来自 verifier。

**为什么这条边界要专门讲**：这是仓库里 `rst_common/judge.py` 已经在守的边界。
LLM 一旦进入 reward，所有数字之间就不可比了。审稿人和 leader 都会问这个，主动说掉。

**可能被问到**

- *「这里说的 verifier 到底检测什么？」* 是任务自带的私有测试脚本，不是模型：`tests/test.sh`
  在容器里跑 `tests/test_state.py`，逐项检查**终态环境**是否满足要求（文件在不在、内容对不对、
  服务起没起），输出每一项的通过与否加一个 0/1 的 reward。它只回答「这件事做成了没有」，
  不判断过程是否合理，也不看轨迹。它是全系统唯一的打分来源，三个 agent 都不能替它打分。
- *「攻击模式的预算 1 到 8 是怎么定的？」* 一个可调的搜索预算，8 是当前的上限设定；
  接受条件只能声称「在预算 B 内存活」，不能声称「不可捷径」——搜索只给上界。
- *「Environment Agent 会不会为了堵反例把 verifier 写成指纹校验？」* 会，这是最大的风险，
  所以有证人集：新 check 必须让所有已知合法解仍然通过。写不出这样的 check 就说明反例是合法解。
- *「三个 agent 都是同一个模型吗？」* 可以是。角色是靠信息集和权限分的，不是靠模型分的：
  攻击模式只看指令和环境，Environment Agent 只能改六个文件。

## 页 4 · The Loop：对抗递归进化怎么做

**一句话**：六步一轮，接受条件有三个合取项，接受时给任务贴一个新标签——首次得手预算。

**口播**

> 一轮六步。
>
> 一，Environment Agent 在 seed 任务上加一个新的终端子目标，产出指令、参数化环境、标准解、verifier。
>
> 二，Verify Agent 在 n 个环境实例上跑标准解加 verifier。**全部通过**才算有通解，
> 只在一个实例上通过不算——这一条就把 RST 的接受条件从「单实例可解」提到了「通解」。
>
> 三，Solving Agent 切到攻击模式，在一个新实例上用 B 条命令预算试图通过 verifier。
> 预算从 1 逐级放大到 8，记录首次得手的预算。
>
> 四，对每个反例，Environment Agent 写一条分离 check：反例失败，标准解和所有证人通过。
> 写得出来，说明 verifier 有缺口，修；**写不出来，说明反例其实是合法解，这道题只是容易，记低难度而不修**。
> 这一条是防止过度特化的关键。
>
> 五，预算内再找不到反例就接受，预算耗尽就拒绝。接受的任务带一个新标签：首次得手预算，它就是难度。
>
> 六，在存活的任务上正常 rollout、筛选、训练。成功轨迹回流成为证人，
> 失败画像告诉 Environment Agent 下一轮先加固哪一类 check。

**底部公式怎么念**：不要逐符号念。说「接受条件是三个合取项：所有实例上标准解通过、
预算内所有攻击都不通过、所有证人仍然通过」，然后指一下第二行「难度是最短通过解的命令数」。

**可能被问到**

- *「为什么必须所有实例都通过才算有通解？」* 只在一个实例上通过的标准解，可能只是针对这份
  fixture 的常数拟合出来的脚本（比如写死了 `LOGSEARCH`），换个实例就失效——它解的是这一份数据，
  不是这道题。在 n 个独立采样的实例上都通过，才说明它是从环境里读出答案的。
  一句话：不要在训练样例上验收。
- *「为什么『写得出分离 check』就说明 verifier 有缺口，写不出就说明题容易？」* 分离 check
  要两头都满足：让反例失败，同时让标准解和所有证人通过。**写得出来**，说明廉价解和合法解
  在终态上存在可观测的差别，只是原来的 verifier 没去看它——那就是漏洞。**写不出来**，说明任何
  能杀掉反例的 check 都会连带杀掉某条合法解，也就是按这道题自己对「做成了」的定义，
  廉价解与合法解不可区分；那它就是一个合法解，这道题本来就不需要多少工作。
  这条规则同时挡住了「把 verifier 写成指纹校验」这种硬堵法，因为指纹必然踩到证人。
- *「n 取多少？」* 报告没定，实践上先取 3 到 5 个实例；这是成本与置信度的取舍，要在实验里定。
- *「第四步谁判断『写不出来』？」* Environment Agent 尝试后由 Verify Agent 裁决：
  任何能杀掉反例的 check 如果同时杀掉某个证人，就判定为写不出来。是可操作的规则，不是主观判断。
- *「这一轮的成本？」* RST 每个接受任务约 0.05 美元。我们多了攻击和重验，
  一个任务的容器运行次数从 1 涨到 5 到 10 次，模型调用增加不多。

**口误红线**：不要说「这样就证明了任务不可作弊」。只能说「在这个信息集和这个预算下没找到捷径」。

## 页 5 · Round 0：起点是一道已经「验收合格」的任务

**一句话**：这道题四项 check 全绿进了任务池，但它检查的全是常数和时间戳。

**口播**

> 举一道真实的题，来自任务池，id 我可以现场调出来。
>
> 指令是：用私钥 SSH 到一台机器，跑一个 Ambari 的配置生成脚本，输出重定向到 result.txt；
> 在 /etc 下找到服务清单，把生成结果里出现而清单里缺少的服务追加进去；
> 再对清单里每个服务确认它出现在结果里，逐行写 `服务名 PASS` 到 validation.txt。
> 听起来是一道正经的长程终端任务。
>
> 环境是这样铺的：清单文件用一条 printf 写死四个服务，远端生成器的输出固定多出一个 LOGSEARCH，
> 标准解里也写死了 `grep -qF "LOGSEARCH"`。
>
> verifier 有四项 check，最后一项就叫「反捷径」。四项都能被标准解通过，这道题进了池。
>
> 但看这四项在查什么：三个固定字符串、一个写死的服务名、两个 mtime 的先后关系。
> **标准解和 verifier 都只对这一个实例成立。** 下一页看它被两个反例推着进化。

**左右两栏的关系**：左边是任务给出的东西（指令 + 环境），右边是验收标准。
要让听众看到：左边写死了 LOGSEARCH，右边就查 LOGSEARCH——这是同一个作者对自己的验证。

**可能被问到**

- *「这道题是你挑出来的极端例子吗？」* 它是普查里的普通样本，不是最差的。全量普查里
  85.7% 的任务是单实例的，这道题的形态是主流。
- *「第 04 项检查 validation.txt 不是清单的逐字复制，这不就是反捷径吗？」* 是，而且它确实堵掉了
  最笨的一种复制。但它堵不掉第 6 页的反例 B：给所有服务写 PASS，文件不是逐字复制，
  mtime 也对，但从未检查过任何一个服务是否真在结果里。

## 页 6 · Evolution：两个反例，两次进化，然后存活

**一句话**：任务没有变长，变的是最短捷径的长度——从 4 条命令、零次 SSH，到必须做任务本身。

**口播**

> 三行，每行一轮。每行左边是当前环境，中间是打进来的反例，右边是修复。
>
> **第一行，Round 0 到 1。** 反例 A 不需要模型，只需要换一个实例：
> Verify Agent 生成 θ₂，这次远端生成器多出来的是 KAFKA 而不是 LOGSEARCH。
> 标准解仍然追加 LOGSEARCH，check 01 仍然要求 LOGSEARCH——**标准解和 verifier 同时失效**。
> 这就是「只对一个实例可解」的直接证据。
> 修复是参数化：缺失服务集合和主机名按 seed 生成；标准解改成算集合差，结果减清单；
> verifier 验证时自己去拉这个实例生成器的真实输出，逐行比对，不再找固定字符串。
>
> **第二行，Round 1 到 2。** 现在写死不行了，于是攻击模式上场，预算 3 条命令：
> 第一条正常跑 SSH 拿结果，第二条把结果里的服务名全部追加进清单，
> 第三条 `sed 's/$/ PASS/'` 给**所有**服务写 PASS。它从来没检查过任何服务是否真在结果里，
> 但 v1 分不清「校验过」和「假定过」，于是通过。
> 修复引入诱饵：清单初值里按 seed 放一个结果中不存在的服务；指令改成逐行写 PASS 或 FAIL；
> verifier 从两个文件重算，PASS 集等于清单交结果，FAIL 集等于清单减结果。
> 反例 B 给诱饵写了 PASS，失败。同时做证人检查：通解版标准解和两条真正逐项校验过的学生轨迹仍然通过。
>
> **第三行，Round 2 存活。** 预算放大到 8 条命令，找不到反例。
> 伪造 result.txt 过不了真实输出比对；不读结果写不出诱饵的 FAIL；复制清单过不了交叉重算。
> 最短通过解必须包含 SSH、集合差、逐项校验。
> 接受，难度标签是「预算 8 存活」。
> 注意对比：Round 0 的最短通过解是 4 条命令、零次 SSH，Round 2 已经等于任务本身。
> **任务没有变长，变的是最短捷径的长度。**

**这一页必须跟着说的一句**（页脚已写）：

> Round 0 是真实任务和真实 verifier 源码；反例 A、B 和修复 v1、v2 是对这份 verifier 的推演，
> 还没有在沙盒里执行过。沙盒的五条 arm 已经写完，实验还没跑。

**可能被问到**

- *「反例 B 是模型找出来的吗？」* 目前是推演。攻击模式里它属于「只写不读」这一类，
  最便宜的实现根本不需要 LLM：一个确定性的模板攻击器就能生成。
- *「诱饵会不会让任务变得不自然？」* 会有这个风险。这就是为什么修复必须过证人检查——
  如果加诱饵之后某条合法的人类解法过不了，这个修复就是不合格的。
- *「怎么知道 Round 2 真的没有捷径？」* 不知道。只知道在这个信息集、这个预算下没找到。
  这是搜索给的上界，报告和口播都必须这样说。

**口误红线**：不要说「进化了两轮之后这道题就安全了」。说「在预算 8 内存活」。

## 页 7 · Evidence：为什么要这么做

**一句话**：两个缺口相加——题目不迫使求解者读实例，模型又已经学会提前收工，
于是现在的数据在教「让验收通过」，不是在教「把事做成」。

**这一页的读法**（讲之前先把这句说出来，八个数字才有意义）

> 上排是**题目的问题**：一道已经合格的题，可以完全不迫使求解者去读这一份实例——
> 答案是常数，抄过去就能过。
> 下排是**模型的表现**：它确实在往「够用就收工」的方向走，做了六成就宣布完成。
> 两个缺口是配套的：只要验收允许，模型就会走那条最省的路。
> 所以要动手的地方不是训练，是**数据生产时的验收标准**。

**口播**（按卡片从左到右的顺序）

> 上面四个是任务侧，全量 37,484 个任务、31 万个测试函数；下面四个是模型侧。
>
> 第一格。**约四分之一的检查（23.9%）不需要从实例重算任何东西就能满足**：
> 只查存在性的 9.2%，只跟常数比的 2.4%，读了产物再跟常数比的 12.3%。
> 最后这一类最要紧——读产物、比常数，那么把标准解的原答案复制过去就能通过。
> 卡片上写了对照面：67.2% 的检查确实在重算或重跑。我不主张 RST 的 verifier 普遍很弱。
>
> 第二格。**只有 14.3% 的任务在构建时引入随机性，剩下 85.7% 是单实例的**，
> 答案是常数，写死在原理上无法检出。这是参数化实例最直接的理由。
>
> 第三格。**599 个 verifier 去读标准解脚本找硬编码值，其中 249 个断言这个脚本存在**——
> 而 `/solution` 只在跑 oracle 时挂载，agent 环境里没有这个目录，
> 所以这 249 个任务对任何 agent 都不可解。这是「设计者只对自己验过」最硬的一条证据。
>
> 第四格是可行性：**64.1% 的任务可以自动生成变异实例**，也就是 24,028 道题能直接进换实例实验。
>
> 下排是模型侧，来自一个 shard、4,429 条干净轨迹。
> 失败轨迹里 91.9% 在最后一步宣称完成，撞到轮数上限的是 0%——
> 失败不是跑不完，是提前收工。
> 失败时已通过的 check 占比中位数是 0.60，做了六成就宣布完成。
> 带编号 check 的那批失败里，35% 最终语义已经通过，挂在过程或反捷径 check 上。
> 最后一个：标准解从 50 行长到 400 行，成功轨迹的中位轮数只从 9 涨到 14。
> **任务在变长，不在变难。**

**可能被问到**

- *「这些数字全量复核过吗？」* verifier 普查是全量的：37,484 个任务、309,712 个函数，
  规则带版本号 `2026-09-04`，manifest 里同时存了「只看函数本体」和「含 helper」两套口径。
  失败画像还是一个 shard 的 4,429 条干净轨迹（全部 Qwen3.5-27B），全量重跑之前不进正式结论。
- *「我记得之前是 26.7%，怎么变成 23.9% 了？」* 旧数字的量级没错，分类错了。
  旧规则只要看到一次 `exists()` 就判「只查存在性」，哪怕函数接着读了文件跟常数比；
  这样错分了 4,161 个函数。修正后正确的说法是把三类合起来：池子 31.7%、全量 23.9%。
  **方向比原来更强，不是更弱。** 这个主动认，比被追出来好。
- *「之前那个 8.5%（整个 verifier 没有任何重算）呢？」* 已经从 deck 上撤下了，因为它对口径极敏感：
  「sweet 池 + 只看函数本体」下是 8.3%，全量加含 helper 下只有 1.2%。要引用就必须带口径。
- *「35% 的分母是什么？」* 是带编号 check 的失败（一个 shard 上是 2,778 条干净失败里的 712 条）。
  分母窄，要说出来。
- *「91.9% 宣称完成，有没有可能是 harness 的机制？」* 有一部分是 Terminus-2 的机制。
  但 0% 撞上限和 0.60 的部分通过是硬事实，这两个不受 harness 影响。
- *「64% 可变异是什么意思？」* 24,028 个任务里有一个「Dockerfile 烤进去、标准解或 verifier 会读、
  标准解不会写」的 fixture，可以自动改一个数据 token。这是沙盒实验的可行性上界。

**口误红线**：这一页最容易翻车。不要说「verifier 很弱」，要说「verifier 从未被负例测试过，
而且 85.7% 的任务答案是常数」。

## 页 8 · Produced Data：生产出来的一条优质数据长什么样

**一句话**：优质在于过程——先探索再动手、错了能诊断恢复、宣称完成前自检、从不碰 verifier。

**口播**

> 最后看产出物。这是同一道题上一条成功轨迹，七个回合，17 条命令，四项 check 全过。
>
> T1 先看密钥在不在，再连接、跑生成器。T2 SSH 成功，看输出内容并定位清单文件。
> T3 发现结果里有 5 个服务，其中 LOGSEARCH 不在清单里——
> **注意这是从输出里读出来的，不是猜的**。T4 追加缺失服务，逐项校验，写报告。
>
> 然后是这条轨迹最值钱的地方。T5 发现 validation.txt 是空的，判断可能是 grep 模式没匹配上，
> 于是手动测试模式、逐个服务检查。T6 模式修正后 5 个服务全部命中，重写报告，
> 并且核对两个文件都非空。T7 逐条对照指令确认五项要求都满足，才宣称完成。
>
> 右边四个标签就是我们要的四种行为：探索、恢复、自检、干净。
> 特别是「恢复」——T4 写出空文件、T5 定位、T6 修正，这是一次真实的错误诊断与恢复，
> 这种片段是长程 agent 最难获得的监督信号。
> 「干净」是说它从未触碰 tests/ 或 verifier，保留了原始 completion 和逐项 check 结果，
> 可以直接重构成训练样本。

**为什么把这一页放在最后**：前面七页都在讲怎么筛掉坏数据，这一页告诉听众筛完之后剩下的是什么。
如果时间不够，这一页可以压到 40 秒，只讲 T5 到 T6 的恢复片段。

**可能被问到**

- *「这条轨迹是这套新系统产出的吗？」* 不是。它是现有任务池上 27B 模型的一条成功轨迹，
  用来说明「优质数据」的标准长什么样。新系统的贡献是让这样的轨迹只能在攻不进去的任务上产生。
- *「页脚写 8 个回合，图上只有 7 个？」* 图上是节选合并展示，文字是模型 analysis 字段的节译。
- *「怎么自动判断一条轨迹有这四种行为？」* `scripts/03g_curate_sft.py` 已有重复命令、
  虚假完成声明等确定性特征；`verifier_fresh`（最后一次改动之后有没有再验证）、
  停滞片段折叠、恢复链、反篡改硬门这四项在 TODO 里，来自那套审计界面的代码。

## 页 9 · Bottom Line

**一句话**：标准解通过只是入场券。

**口播**

> 收一下。对抗递归进化：每一轮，求解者攻击环境，环境在验证者的裁决下进化，
> 存活的任务才进入训练。
> 标准解通过只是入场券，还要满足三件事：在预算内找不到捷径、此前的合法解仍然通过、
> 换一个实例之后答案不再是常数。
> 三个 agent 各管一段，verifier 始终是唯一的 reward。
>
> 一句话对比 RST：他们做可解性递归，我们做反捷径鲁棒性递归。

**如果被问「下一步做什么」**：三步，都不需要训练、不需要 LLM 设计者。
verifier 全量普查（已完成）；20 个任务的沙盒实验，五条 arm 验证「换一个实例后标准解是否还成立、
原答案复制过去是否还能过」（代码就绪，未执行）；从 61,575 条成功轨迹里筛出廉价成功并在沙盒里回放。
第二步的结果决定整套叙事成不成立。
